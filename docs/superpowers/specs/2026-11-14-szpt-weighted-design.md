# СЗПТ, фаза 2: весовые товары и новые группы — дизайн

> Historical design or rollout plan. For current deployment and rollback, see the [Frontend VPS runbook](../../production/FRONTEND_VPS_DEPLOYMENT.md).

Дата: 2026-11-14. Статус: согласован в чате, ждёт проверки спецификации пользователем.
Продолжение [фазы 1](2026-11-12-scrum-25-szpt-design.md) (SCRUM-25, раздел живой с 2026-11-12, прод API `98427c3`).

## Зачем

Раздел СЗПТ показывает 10 позиций из 31 по приказу МТИ РК № 362-нқ. Анализ снимка прода 2026-11-14 показал:
ещё 4 позиции есть в каталоге с фасовкой (сахар-песок, мука 1 сорта, рожки, хлеб), а ещё 10 позиций лежат в
каталоге почти целиком **весовыми** товарами (овощи, яблоки, говядина, курица, фарш), которые фаза 1 сознательно
не брала: у них нет фасовки, цена у них за кг. Пользователь хочет добавить всё, что можно добавить сейчас, и
показывать у весовых честную цену за кг, сравнимую между сетями.

Цели:

- 15 новых групп (итого 25, они покрывают 26 из 31 позиции приказа) по таблице раздела «Группы»;
- весовой товар входит в группу и показывает цену за кг, посчитанную по пометке сети, а не по догадке из названия;
- в группах с весовыми товарами сравнение по умолчанию идёт по цене за кг.

Не цели: ₸/кг в обычном каталоге и на странице товара; изменения pipeline, parser, sync на VPS; добавление весовых
товаров в 10 текущих групп (см. «Решения»); баранина, конина, рыба, чай, соль (нет данных или категорий); фильтр
«только на развес».

Анти-цели (провал, даже если «работает»):

- ложная цена за кг: товар продаётся упаковкой неизвестного веса, а сайт показывает его цену как «₸/кг»;
- весовой товар в сортировке «Дешевле за упаковку» среди упаковок, как будто его цена — цена упаковки;
- изменение поведения 10 живых групп (состав, порядок по умолчанию, URL).

## Данные

### Откуда известно, что цена весовая

Каждая сеть сама помечает весовой товар, парсер приводит цену и кладёт признак в `raw_products."rawPayload"`
(логика — `pipeline/src/mapping/weight.ts`, `isVariableWeight`):

| Сеть | Признак весового | Цена в `offers.price` относится к |
|---|---|---|
| DINA | `price_type = 'weight'` или `isWeightProduct = true` | `pricePerUnitMultiplier` грамм (1000, либо вес из названия) |
| ANVAR | `priceUnit = 'kg'` (оффер `quant KGM`) | `pricePerUnitMultiplier` грамм (1000, либо вес из названия) |
| DANA | `priceUnit = 'kg'` (подпись «/кг») или в названии `PLU:1234` / «вес», «весовой» | 1000 грамм (множителя нет) |
| FIX_PRICE | весовых нет | — |

Публикация (`pipeline/src/mapping/publish.ts`) не склеивает весовые предложения со штучными в один канонический
товар, поэтому у канонического товара предложения либо все весовые, либо все штучные.

API этот признак сейчас не видит: роль `aktau_api_reader` читает `stores, store_locations, categories,
canonical_products, offers, snapshots` и не имеет доступа к `raw_products` (миграция
`20261004000000_rls_runtime_access`).

### Оценка групп (публичный API, снимок 2026-11-14, регулярки приближённые)

| Группа | Товаров | С фасовкой | Сети |
|---|---:|---:|---|
| Сахар-песок | 18 | 18 | ANVAR, DANA, DINA |
| Мука пшеничная 1 сорта | 26 | 26 | ANVAR, DANA, DINA |
| Рожки | ~84 | 84 | ANVAR, DANA, DINA |
| Хлеб пшеничный | ~10 | ~10 | DANA, DINA |
| Говядина | ~15 | 0 | ANVAR, DINA |
| Мясной фарш (не куриный) | ~10 | ~4 | DANA, DINA, ANVAR |
| Мясо кур | ~27 | 0 | ANVAR, DANA, DINA |
| Куры (тушка) | ~16 | 4 | ANVAR, DANA, DINA |
| Картофель / морковь / лук / капуста | 5 / 4 / 2 / 2 | 0 | 2–3 сети |
| Помидоры / огурцы / яблоки | 3 / 3 / 10 | 0 | 2–3 сети |

Сколько из товаров без фасовки реально помечены сетью как весовые, публичный API не показывает — это даст
интеграционный тест и read-only SQL на проде перед релизом (раздел «Релиз»). Товар без фасовки и без пометки
в группу не входит (пример: «Фарш куриный Namir замороженный», 730 ₸ — скорее всего пачка).

## Решения пользователя (2026-11-14)

- Добавить все 15 групп сейчас; хлеб — «широко»: белый пшеничный хлеб с весом в названии (критерий приказа
  «из муки 1 сорта» по названию не проверить, позже можно сузить).
- В группе, где допускаются весовые товары, сортировка по умолчанию — «Выгоднее за кг». В «Дешевле за упаковку»
  весовые идут в конце. На карточке весового товара главная цифра — «2 780 ₸/кг» и пометка «на развес».
- Признак весового API берёт из узкого представления в базе (подход 1 ниже).
- Состав групп — таблица раздела «Группы» (согласована в чате).

## Подходы

1. **Узкое представление `offer_price_basis` (выбран).** Миграция создаёт view над `offers ⨝ raw_products ⨝ stores`
   с тремя полями на предложение: id предложения, «весовой» и «цена за N грамм». `aktau_api_reader` получает
   SELECT только на view, не на `raw_products`. Работает на текущем снимке сразу после миграции, точен для
   каждого предложения, pipeline и sync не меняются. Цена: миграция на проде (дамп перед ней) и порядок релиза.
2. **Пометка в `canonical_products.attributes` из pipeline.** Без миграции, но меняет ежедневный sync на VPS
   (самая хрупкая часть прода), работает только со следующего снимка, а атрибуты проходят через словарь
   сопоставления — новое поле пришлось бы держать вне ключа матчинга. Отклонён.
3. **Эвристика в API** («в овощных и мясных группах без фасовки — значит за кг»). Самый быстрый, но даёт ложную
   цену за кг у упаковок с нераспознанным весом — прямо нарушает анти-цель. Отклонён.

Предложенное в чате разбиение релиза на два шага (сначала фасованные группы, потом весовые) не нужно: фронт
выкатывается первым и совместим со старым API (раздел «Релиз»), поэтому один релиз API включает всё сразу.
Решение агента.

## Часть 1. База: представление `offer_price_basis`

Новая миграция `backend/prisma/migrations/2026111400000_offer_price_basis/migration.sql` (имя по образцу соседних,
точную метку времени выбирает исполнитель):

```sql
CREATE VIEW public.offer_price_basis AS
SELECT o.id AS "offerId",
       w.weighted AS "soldByWeight",
       CASE WHEN w.weighted THEN
         CASE WHEN jsonb_typeof(r."rawPayload"->'pricePerUnitMultiplier') = 'number'
                   AND (r."rawPayload"->>'pricePerUnitMultiplier')::numeric > 0
              THEN (r."rawPayload"->>'pricePerUnitMultiplier')::numeric ELSE 1000 END
       END AS "basisGrams",
       o."snapshotId" AS "snapshotId"
FROM public.offers o
JOIN public.raw_products r ON r.id = o."rawProductId" AND r."snapshotId" = o."snapshotId"
JOIN public.stores s ON s.id = o."storeId"
CROSS JOIN LATERAL (SELECT CASE s.code::text
  WHEN 'DINA'  THEN coalesce(r."rawPayload"->>'price_type' = 'weight', false)
                 OR coalesce(r."rawPayload"->>'isWeightProduct' = 'true', false)
  WHEN 'ANVAR' THEN coalesce(r."rawPayload"->>'priceUnit' = 'kg', false)
  WHEN 'DANA'  THEN coalesce(r."rawPayload"->>'priceUnit' = 'kg', false)
                 OR r."rawName" ~* '(^|[^а-яa-z])вес(ов(ой|ая|ое|ые))?([^а-яa-z]|$)|(^|[^a-z0-9_])PLU\s*[:;]\s*[0-9]+'
  ELSE false END AS weighted) w;

GRANT SELECT ON public.offer_price_basis TO aktau_api_reader;
```

- Логика — то же правило, что `isVariableWeight` (границы слова записаны классами вместо ``/lookbehind, набор
  букв тот же `[а-яa-z]`); интеграционный тест проверяет оба варианта DANA (`PLU:1231`, «весовой»).
  Комментарий в SQL и в `weight.ts` ссылается друг на друга, чтобы правка одного места напоминала о втором.
- Миграция сама проверяет, что view сможет читать `raw_products` в обход RLS: владелец view (роль, выполняющая
  миграцию) — владелец `raw_products` или имеет `BYPASSRLS`, и `raw_products` без `FORCE ROW LEVEL SECURITY`;
  иначе `RAISE EXCEPTION` (по образцу guard-блока `rls_runtime_access`). Без этого view молча вернула бы 0 строк.
  Решение агента.
- View создаётся владельцем таблиц и выполняется с его правами (`security_invoker` не включаем): RLS на
  `raw_products` для `aktau_api_reader` остаётся закрытой, наружу видны только четыре столбца. `FORCE ROW LEVEL
  SECURITY` в проекте не используется (проверка в миграции `rls_runtime_access`), поэтому владелец читает
  `raw_products` через view без политики. `REVOKE ALL ... FROM PUBLIC`, `anon`, `authenticated` — как в
  `price_history`.
- Prisma схема view не описывает (как и политики); `prisma migrate deploy` применяет SQL как есть.
- `"snapshotId"` (столбец `offers`) нужен, чтобы API фильтровал view по снимку: условие
  `b."snapshotId" = <снимок>` в `ON` левого соединения PostgreSQL проталкивает внутрь view, и `offers` и
  `raw_products` читаются только за один снимок, а не за все 14 хранимых.
- Откат (только после отката API, иначе новый API упадёт на запросах):
  `DROP VIEW public.offer_price_basis;` и
  `DELETE FROM public._prisma_migrations WHERE migration_name = '20261114000000_offer_price_basis'` в той же транзакции, что и `DROP VIEW` (проверено 2026-11-14 на локальной базе: `prisma migrate resolve --rolled-back` для успешно применённой миграции падает с P3012, а строка с `rolled_back_at` по-прежнему считается применённой) — иначе `_prisma_migrations`
  считает миграцию применённой и следующий `migrate deploy` view не создаст. Данные не трогаются, старый API
  view не читает.

## Часть 2. API

Внешне — только аддитивные поля. Существующие клиенты не ломаются.

### Правила групп (`backend-go/internal/szpt/groups.go`)

`Rule` получает поле `Weighted bool` — группа допускает весовые товары. Для таких групп:

- `Unit` обязательно `Kg` (unit-тест на список);
- исключение `weighted` по названию («вес», «весов») не добавляется — весовые определяются по view;
- сортировка по умолчанию — `unit_price_asc`.

Для 10 текущих групп `Weighted = false`, и для них view **не используется вообще**: членство, цена за единицу,
сортировка и `soldByWeight = false` — ровно как в фазе 1 (в т.ч. «Сыр … Березка 50% вес» по-прежнему исключён по
названию, а пачка с фасовкой, помеченная сетью весовой, остаётся в группе). Так анти-цель «живые группы не
меняются» выполняется по построению, а не по совпадению фикстуры. Сколько таких помеченных товаров сейчас в живых
группах, показывает SQL перед релизом (часть 6); если они есть, их цену за единицу стоит проверить отдельно —
это отдельное решение, не эта задача. Решение агента.

### Членство товара в группе (SQL `szptMembersSQL`)

В `usable` добавляются, по предложениям текущего снимка в наличии (`LEFT JOIN offer_price_basis` по `offerId` и
`snapshotId` = снимок запроса;
нет строки во view — предложение считается штучным):

- `by_weight` = `bool_and("soldByWeight")` — все предложения товара весовые;
- `unit_weight_exact` = `min(price * 1000 / "basisGrams")` по весовым предложениям.

Для `Weighted` групп товар входит, если выполнены прежние условия по категории, шаблонам, исключениям и жирности,
и при этом:

- `by_weight` ложно и фасовка известна и `≥ min_size` (как сейчас), **или**
- группа `Weighted`, и `by_weight` истинно (фасовка не нужна и не проверяется).

Весовой товар с весом в названии (Dina: «Цыплёнок-бройлер KOKO 1.8 кг», цена за 1 800 г; граммы в названии
Dina не разбирает — там множитель 1000, Anvar разбирает и граммы) считается весовым, его фасовка в `sizes`
не попадает; цена за кг всегда считается по сохранённому множителю, а не по названию. Товар со смешанными предложениями (часть весовые) после `publish.ts` не ожидается; если встретится —
считается штучным и требует фасовку, а цену за единицу каждого предложения API считает по его собственному признаку.

### Цена за единицу

- Штучное предложение: как в фазе 1, `price × factor / size`.
- Весовое предложение: `price × 1000 / basisGrams`, единица `kg`.
- `unitPrice` товара = минимальная из цен за единицу его предложений (для штучного товара совпадает с фазой 1:
  у всех предложений одна фасовка). `minPrice` товара не меняется — это минимальная цена предложения, как в каталоге.
- Округление, как в фазе 1: до 2 знаков half-up только в ответе, сортировка по точному `numeric`.

### Сортировка

- `price_asc`: сначала штучные по `min_price`, затем весовые по точной цене за кг; затем `min_price`, затем `id`
  (`COLLATE "ru-x-icu"`): `ORDER BY by_weight, CASE WHEN by_weight THEN unit_exact ELSE min_price END, min_price, id`.
- `unit_price_asc`: точная цена за единицу товара (минимум по предложениям), затем `min_price`, затем `id`.
  Весовые и штучные смешиваются — это и есть «честное сравнение».
- Без параметра `sort` эндпоинт использует сортировку группы по умолчанию (`price_asc` для обычных, `unit_price_asc`
  для `Weighted`). Явный `sort=price_asc` в весовой группе допустим.

### Ответы

`GET /api/szpt`: у группы новое поле `defaultSort` (`price_asc | unit_price_asc`). `count` включает весовые
товары, `sizes` — только фасовки штучных (у группы только из весовых `sizes` = `[]`). Группа без товаров по-прежнему
не возвращается.

`GET /api/szpt/{group}/products`: у товара и у каждого предложения новое поле `soldByWeight` (boolean). Фильтр
`size` выбирает штучные товары этих фасовок; весовые при выбранной фасовке не показываются. Для групп с пустым
`sizes` любой `size` → 400 (как сейчас: значения нет в `sizes`).

### Код и контракт

- `szpt.Rule.Weighted`, `szpt.Group.DefaultSort`, `szpt.Product.SoldByWeight`, `szpt.Offer.SoldByWeight`;
  `PriceOf` получает вариант для весового предложения (или общий вход «цена, количество в базовой единице»).
- `postgres/szpt.go`: join view, `by_weight`, условие членства, `unit_exact` как минимум по предложениям, два ORDER BY,
  сортировка по умолчанию из правила; признак весового предложения нужен и при сборке `offers[]` (сейчас их
  гидрирует общий `attachOffers` каталога — его DTO не меняем, признак берётся отдельным запросом или колонкой
  в SZPT-ветке).
- `contracts/openapi.yaml` + `contracts/examples/szpt-*.json`: три новых поля, пример весового товара и группы с
  `defaultSort: unit_price_asc`.
- Изменения в `contracts/` и `backend/prisma` (новая миграция) — оба пути в `protectedPaths`
  (`scripts/deploy/auto-transport.mjs`): если релиз пойдёт через workflow/broker, нужны blob-pinned записи в
  `approvedExceptions` для каждого изменённого файла; ручной cutover-путь эту проверку не запускает.

## Часть 4. Фронт

Фронт совместим со старым API: новые поля необязательны в типах, при их отсутствии поведение как в фазе 1.

- `api/types.ts`: `SzptGroupDto.defaultSort?`, `SzptProductDto.soldByWeight?`, `offers[].soldByWeight?`.
- `lib/szpt.ts`: `readSzptState` берёт сортировку из `?sort=` (оба значения) или `group.defaultSort ?? 'price_asc'`;
  `szptParams` не пишет `sort`, если он равен сортировке группы по умолчанию, — для этого получает группу.
- Подзаголовок: «{{count}} позиций из перечня СЗПТ (приказ МТИ РК № 362-нқ).» — `count` = число групп из API
  (склонение ru: позиция/позиции/позиций; kk: «ӘМАТ тізімінен {{count}} позиция»). «Говядина» за две позиции
  приказа в счётчике не удваивается — счётчик значит «групп в разделе», формулировку уточнит исполнитель так,
  чтобы не обещать 26 при 25 чипах.
- Фасовка: блок не показывается, если `sizes` пустой (уже так в `SzptPage`).
- Карточка (`ProductCard`) получает `soldByWeight`. Если истинно: главная цифра — `unitPrice` («2 780 ₸/кг»),
  рядом мелкая пометка «на развес» / «салмақпен»; строки предложений показывают цену за кг каждой сети; второй
  строки «₸/кг» под главной цифрой нет. Иначе — как в фазе 1.
- i18n: имена 15 групп в `kk.json` (`szpt.groups.*`), пометка «на развес», новый подзаголовок с числом.
- `mockAdapter` и `mocks/szpt.json`: одна весовая группа (например, `potatoes`) и смешанная (`minced-meat`).
- Чипов становится 25: на десктопе колонка в сайдбаре длиннее, на мобильном — та же горизонтальная прокрутка.
  Группировка чипов по разделам не делается.
- Sitemap получает новые группы автоматически из `/api/szpt`.

## Часть 6. Релиз

1. **PR 1 — миграция, API, контракт, эта спека и план.** CI зелёный → merge. На прод не выкатывается.
2. **PR 2 — фронт.** Merge → Vercel. Со старым API фронт ведёт себя как в фазе 1 (новых полей нет, групп 10,
   подзаголовок «10 позиций»). Проверка `/ru/szpt/rice`, `/kk/szpt/rice` без регрессий.
3. **Перед миграцией** (команды на VPS вводит пользователь, агент пишет и проверяет вывод):
   - свежий дамп базы (последний — 2026-11-07);
   - read-only SQL на последнем снимке: сколько предложений каждая сеть помечает весовыми, распределение
     `pricePerUnitMultiplier`, сколько DANA-товаров весовые только по названию; сколько помеченных весовыми
     товаров сейчас в 10 живых группах (для сведения, см. часть 2); сверка с ожиданиями фикстуры;
   - **стоп-критерии** (решение агента): у DINA, ANVAR или DANA 0 весовых предложений в снимке — значит, признак
     не сохраняется, релиз останавливается и разбирается; тонкая группа (1 сеть) или пустая группа — не стоп:
     пустые группы API скрывает, тонкие показываются как есть;
   - не во время sync (01:00 и 13:00 UTC).
4. **Миграция** `prisma migrate deploy` (view + GRANT; guard-блок проверяет владельца и RLS). Проверка:
   число строк view для последнего снимка = числу его предложений и расхождений с правилом 0 (иначе view молча
   теряет строки — стоп, откат view, как ниже); `aktau_api_reader` читает view, но не `raw_products`; старый API
   работает (view он не использует). Затем гейт латентности (план, Task 10 Step 4): `EXPLAIN (ANALYZE, BUFFERS)`
   запроса товаров СЗПТ для живой и весовой группы ролью API; дольше 300 мс или дольше 3× времени текущего
   `/api/szpt` — стоп, API не выкатывается.
5. **Релиз API** ручным путём, как `98427c3` (build-only workflow → артефакт → копирование на VPS →
   cutover-скрипт с авто-откатом). Точка отката — активный релиз (`98427c3`). Дополнительные smoke: `GET /api/szpt` →
   200, групп больше 10, у весовой группы `defaultSort = unit_price_asc`; `GET /api/szpt/potatoes/products` → 200.
6. **Проверка на проде:** число товаров по группам против таблицы «Оценка» (±30% — у весовых оценка грубая),
   ручная выборка товаров каждой новой группы на ложные вхождения, сверка 3–5 цен за кг с сайтами сетей.
   Ложные вхождения → hotfix-правка регулярок, как `98427c3`.
7. **Закрытие:** «Current release» в `deploy/README.md`, отчёт о релизе, память. Комментарий в Jira — по решению
   пользователя.

Откат: фронт — откат деплоя Vercel (не нужен: со старым API он совместим); API — авто-откат cutover-скрипта на
`98427c3`; view — только после отката API (иначе новый API упадёт на запросах): `DROP VIEW public.offer_price_basis;`,
и в той же транзакции удалить строку миграции из `_prisma_migrations` (`migrate resolve --rolled-back` здесь не
работает, P3012), чтобы следующий `migrate deploy` создал view заново.
