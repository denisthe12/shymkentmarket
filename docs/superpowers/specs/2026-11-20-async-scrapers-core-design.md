# Асинхронные парсеры: общий каркас и первый магазин Magnum

Дата: 2026-11-20. Ответственный: Backend 2. Статус: проект на согласование.

## Зачем

Shymkent Market собирает цены магазинов Шымкента на социально значимые продукты (СЗПТ: 30 групп,
31 позиция перечня по приказу МТИ РК № 362-нқ), как Aktau Market делает это для Актау.
Унаследованные парсеры (`pipeline/src/scrapers/`: Dina, Dana, Fix Price, Анвар) написаны под магазины
Актау. Они медленные: `politeFetch` ждёт 300 мс перед каждым запросом, ежедневный прогон Анвара
занимает ~150 с, Dana ~105–135 с. Нужны новые парсеры: быстрые, асинхронные, на общем каркасе.

Каркас не привязан к городу. Если новые парсеры хорошо покажут себя в Шымкенте, их переносят
в Aktau Market. Первый магазин — Magnum, источник — API приложения Magnum Go. Потом добавятся
другие магазины Шымкента.

## Цели

- Общий каркас для всех будущих магазинов: асинхронные запросы с лимитами, повторами и таймаутами,
  проверка полноты, единая статистика прогона.
- Модуль Magnum, который собирает все товары категорий, нужных для СЗПТ, по Шымкенту.
  В модуле есть таблица «категория Magnum → категория сайта»: по ней выбирается, что скачивать,
  и из неё во втором проекте заполнится словарь Шымкента.
- Выход в существующем формате `SourceFile` (`pipeline/src/types.ts`). `sync` и Go `ingest`
  в этом проекте не меняются.

Это первый из двух отдельных проектов. Второй — **данные Шымкента**: новый словарь (заполняется
из таблиц категорий модулей), фильтры таксономии по данным Шымкента, замена данных Актау
(`data/mapping/*`, `data/snapshots/*`, значение `SYNC_STORES` по умолчанию) и сквозная проверка
до `/api/szpt`. Он описывается своим документом. Из Aktau Market Шымкент берёт только общий код
без привязки к городу; данные делаются заново.

## Критерии «работает хорошо»

Эти критерии решают, пора ли переносить парсеры в Актау.

| Критерий | Как проверяем |
| --- | --- |
| Скорость | Каждый прогон пишет в `sourceStats` время, число запросов и повторов. На Актау новый парсер магазина должен быть хотя бы в 3 раза быстрее старого и собирать тот же набор товаров. Для Magnum эталона нет: время первого прогона записываем как ориентир. |
| Полнота СЗПТ | Каждая категория из scope скачана до последней страницы. Если API отдаёт итог, число позиций совпадает с ним. Ошибок 0. В этом проекте: по каждой из 12 публикуемых категорий сайта есть товары Magnum. Проверка по 30 группам СЗПТ (правила групп живут в Go) — во втором проекте, на сквозном прогоне. |
| Стабильность | 429 и 5xx переживаются повторами с учётом `Retry-After`. Частично упавший скрап не записывается, и прежний файл остаётся. Ежедневный локальный прогон 7 дней подряд проходит без сбоев. |

## Не цели

- Словарь Шымкента, таксономия, замена данных Актау и публикация: второй проект.
  Унаследованный `data/mapping/dictionary.json` — словарь Актау; в этом проекте его не трогаем
  и Magnum в него не добавляем.
- Сопоставление товаров разных магазинов в общие карточки (`agent:classify`, `agent:match`,
  `dict:apply`). С одним магазином сопоставлять нечего; задача появится со вторым магазином.
- Переписывание парсеров Актау на новый каркас. Это отдельная задача после того, как каркас пройдёт
  критерии в Шымкенте.
- Расписание, сервер, продакшн-БД Шымкента (их пока нет).
- Каталог акций с сайта magnum.kz. Он отдаёт только акции недели (136 товаров по Шымкенту
  на 2026-11-20), а не полный ассортимент.

## Анти-цели

Работа провалена, даже если код технически работает, если:

- парсер перегружает сервер магазина так, что получает блокировку или много 429;
- частично собранный файл попадает в `sync` и публикует урезанный набор цен;
- в публичный репозиторий попадают токены, сырые ответы API, личные данные или описание того,
  как был найден API источника;
- каркас нельзя перенести в Aktau Market без правок под город.

## Ограничения

- Репозиторий публичный. Фикстуры в тестах обезличены, без токенов, cookie и идентификаторов устройства.
  Рабочие заметки об API хранятся только вне репозитория. В коде, комментариях, документах и PR нет
  описания способа, которым получены сведения об API.
- БД Шымкента нет. Все прогоны и проверки идут локально. Запись в БД разрешена только
  в проверенную одноразовую PostgreSQL (`AGENTS.md`).
- Живой скрап реального магазина запускаем только после явного «да» пользователя на этот источник.
- Стек pipeline: TypeScript, Node, pnpm 10.32.1, vitest, zod. Новых зависимостей не добавляем.
- Зона Backend 2: `pipeline/`, `backend/prisma/`. Go API (Backend 1) не меняем.

## Подходы

| Подход | Суть | Плюсы | Минусы | Решение |
| --- | --- | --- | --- | --- |
| **А. Своё ядро** | Встроенный `fetch` Node, своя очередь задач, лимитер параллельности и скорости, повторы | Ноль зависимостей, всё под тестами, переносится одной папкой | Очередь, лимиты и повторы пишем и поддерживаем сами (~300–400 строк) | **Выбран пользователем** |
| Б. Библиотеки | `p-queue`, `p-retry`, `undici` | Меньше своего кода | Три зависимости переносить в Актау и обновлять; поведение при 429 всё равно настраивать | Отклонён |
| Crawlee | Фреймворк обхода сайтов | Очередь, сессии, прокси из коробки | Тяжёлый, рассчитан на браузер, для JSON-API лишний | Отброшен |
| Python / Go | Парсер на другом языке | Python aiohttp / Go быстры | Pipeline на TypeScript, стек разделился бы в обоих проектах | Отброшен |

Скорость упирается в то, сколько параллельных запросов выдерживает сервер магазина, а не в язык.
Поэтому главное — параллельность, переиспользование соединений и отсутствие фиксированных пауз,
при соблюдении лимита.

## Устройство

### Расположение

```text
pipeline/src/scrape/
  core/          каркас: без ссылок на город и конкретные магазины
  stores/magnum/ модуль Magnum
```

Перенос в Актау: скопировать `core/`, подключить модули магазинов и перенести правку
`pipeline/src/types.ts`: `SourceFileSchema.city` — непустая строка, а не литерал `'Aktau'`
(`core/` собирает `SourceFile` с `city` из модуля магазина). `core/` не импортирует
ничего из `stores/` и из унаследованных `scrapers/`.

### Каркас (`core/`)

**HTTP-клиент.** Обёртка над встроенным `fetch`:

- таймаут каждого запроса (`AbortSignal.timeout`);
- повтор при сетевой ошибке, таймауте, 429 и 5xx; растущая пауза со случайным разбросом;
  максимум повторов настраивается;
- при 429/503 с `Retry-After` (секунды или дата) ждём указанное время, но не дольше заданного предела;
  без `Retry-After` пауза после 429 не короче базовой;
- пауза после 429/503 общая: лимитер не начинает ни одного запроса, пока она не прошла;
- прочие 4xx — сразу ошибка без повтора;
- счётчики: запросы, повторы, 429, 5xx, таймауты, суммарный объём;
- заголовки по умолчанию задаёт модуль магазина.

**Лимитер.** Ограничивает одновременно идущие запросы (concurrency) и число запросов в секунду
(token bucket). Пауза появляется только тогда, когда лимит исчерпан. Повтор после 429 тоже проходит
через лимитер, поэтому всплеск 429 сам снижает темп.

**Очередь задач.** Задача — единица работы модуля, например «страница N категории X».
Обработчик задачи может поставить новые задачи. Типичный сценарий: первая страница категории сообщает
число страниц, остальные сразу встают в очередь и идут параллельно. Ошибка задачи (после всех
повторов) записывается с контекстом (категория, страница, причина) и увеличивает `errorCount`.
После первой такой ошибки новые задачи не запускаются: уже идущие доходят до конца, остальные
пропускаются, повторный пересчёт категорий не делается. Файл всё равно будет отклонён, а сервер
не нагружается дальше. В `sourceStats` пишутся `skipped` (число пропущенных задач) и `aborted`.
Невалидный товар и расхождение с итогом — тоже ошибки, но прогон они не останавливают.

**Запуск магазина.** Принимает модуль и настройки, выполняет все задачи и собирает `SourceFile`:

- товары без дублей по `sourceProductId` (товар может стоять в нескольких категориях);
  `sourceCategoryPath` берётся из первой категории scope, в которой товар встретился;
- проверка полноты: если модуль сообщил ожидаемый итог категории, собранное число сравнивается
  с ним; расхождение — ошибка;
- `sourceStats`: время прогона, счётчики HTTP, число задач, по каждой категории scope
  «собрано / ожидалось», лимиты прогона;
- каждый товар проходит `SourceProductSchema`; невалидный товар — ошибка с контекстом, а не падение
  всего прогона.

**Контракт модуля магазина** (точную форму типов выбирает исполнитель):

- `storeCode`, `city`;
- лимиты по умолчанию (concurrency, rps) и их максимумы;
- необязательная подготовка: получение гостевого токена, выбор магазина или склада в городе;
- стартовые задачи: категории scope;
- обработчик задачи: делает запрос через клиент каркаса, разбирает ответ и возвращает товары,
  новые задачи и, если известен, ожидаемый итог категории.

**Настройки из env.** `<STORE>_CONCURRENCY` и `<STORE>_RPS` переопределяют лимиты в пределах
максимумов модуля. Мусор, ноль и дроби дают значение по умолчанию с предупреждением, как
`resolveDanaConcurrency` в `pipeline/src/scrape-policy.ts`.

### Интеграция с существующим pipeline

- `pipeline/src/types.ts`: `MAGNUM` в `STORE_CODES`; `city` в `SourceFileSchema` перестаёт быть
  литералом `'Aktau'` и становится непустой строкой. Город задаёт модуль магазина. Go `ingest` поле
  `city` не читает (проверено по `backend-go/internal/ingestion`).
- Признак весового товара и единица цены Magnum сохраняются в `rawPayload` в явных полях
  (только из полей API, никогда из названия товара). Их использование при публикации — во втором
  проекте: ветка `MAGNUM` в `isVariableWeight` (`pipeline/src/mapping/weight.ts`), в представлении
  `offer_price_basis` и в `ops/postgres/szpt/offer_price_basis_check.sql` (три места меняются
  вместе), а также значение `MAGNUM` в enum `StoreCode` Prisma и строка магазина в `stores`
  (по образцу миграций `20261102000000_store_anvar_enum` и `20261102000100_store_anvar_rows`).
- CLI: `pnpm scrape:magnum` через реестр `SCRAPERS` в `pipeline/src/cli/scrape.ts`; файл
  `magnum.json` пишется в тот же каталог источников. Для новых парсеров любой `errorCount > 0`
  означает отказ записывать файл (прежний остаётся), по образцу `assertCompleteScrape`.

### Модуль Magnum

Известно на 2026-11-20:

- источник — API приложения Magnum Go; город — Шымкент;
- scope — категории Magnum, соответствующие публикуемым категориям сайта
  (`DEFAULT_PUBLISH_CATEGORIES` в `pipeline/src/mapping/scope.ts`: milk, dairy, eggs, bread, meat,
  vegetables (включая фрукты, нужны яблоки), groats, sugar, oil, salt, tea-coffee, fish).
  Таблица «ID категории Magnum → slug категории сайта» хранится в модуле как данные (по образцу
  `ANVAR_SCOPE` в `pipeline/src/scrapers/anvar.ts`, но со slug в явном поле, а не в комментарии).
  Тест проверяет, что все slug из таблицы — публикуемые категории и что каждая из 12 категорий
  покрыта хотя бы одной категорией Magnum.
- Если API требует постоянный ключ приложения или секрет подписи, модуль читает его из env
  (`MAGNUM_*`). В репозиторий он не попадает; тесты используют поддельное значение; в документах
  пишется только имя переменной.

#### Факты об API (на 2026-11-21)

**Адрес и формат.** `https://mgo-gw1.e-magnum.kz` (`mgo-gw2` — равноправное зеркало с теми же путями).
Только `GET` с query-параметрами, ответы JSON (gzip). Запросы идут с `accept: application/json`; других обязательных заголовков нет.

**Авторизация — гостевой токен, постоянного ключа нет.** `POST /auth/server/api/v1/security/guest/login`
с пустым телом, без заголовка авторизации, отдаёт `{ token, refreshToken }`; `token` уже содержит
префикс `Bearer ` и подставляется в `authorization` как есть. Срок жизни 10 часов, поэтому модуль
берёт один токен в начале прогона и не обновляет его. Запросы каталога идут с этим заголовком.
Переменные `MAGNUM_*` для ключа не нужны.

**Магазин.** Цены и наличие привязаны к складу (`platformId`). Для Шымкента это даркстор
`7001` («Шымкент, Бекжан»): `GET /productstore/geo/api/v1/type/all/attributes?latitude=…&longitude=…`
(без авторизации) для точек в Шымкенте отдаёт `darkStore.id = 7001`. Модуль хранит `7001` как
данные и при запуске сверяет его этим запросом по координатам центра города; несовпадение — ошибка
прогона.

**Дерево категорий.** `GET /catalog/client/catalog?platformId=7001&parentId=<id|пусто>&includeChildNodes=true` —
массив узлов `{ id, name, parentId, orderId, askAge, childCategories[] }`, два уровня за запрос.
Корень `11` «Продукты» содержит группы (`1107`, `1101`, …), у групп листья с шестизначными ID
(`110702` «Молоко»). Товары запрашиваются по листьям. Корни `51` (сезонный) и `60` «Акции»
дублируют товары обычных листьев и в scope не входят. Товар может лежать в нескольких листьях
(поле `categories`), поэтому дедупликация по `itemId`.

**Список товаров листа.** `GET /catalog/client/platformItemV2?platformId=7001&categoryIds=<лист>&sortTypeColumn=sales&sortOrder=DESC&pageId=<0..>&pageSize=20&filterIds=` —
Spring-страница `{ content[], number, size, numberOfElements, totalElements, totalPages, last }`.
Сервер отдаёт по 15 позиций, какой бы `pageSize` ни был запрошен. **Итога категории нет:**
`totalElements` равен числу позиций, отданных по текущую страницу включительно, `last` всегда
`true`. Конец листа — страница, где `numberOfElements < size` или `content` пустой. Сверка
с итогом API для этого эндпоинта невозможна, `total = null`.

**Карточка товара** (`GET /catalog/client/platformItem/<itemId>`) — тот же объект, плюс
`itemLeftovers`. Для парсера не нужна.

**Поля товара.**
- `itemId` — ID позиции на складе (ключ дедупликации); `extId` — сквозной артикул Magnum;
  `barcodes[]`; `name`; `descr`.
- `price` — текущая цена **в тиынах** (целое; `/100` даёт тенге, по данным на 2026-11-21 всегда кратно
  100). `discount.prevPrice` (тоже в тиынах) — цена до скидки, есть только у товаров со скидкой.
  `isPromo` по данным на 2026-11-21 всегда `false`; признак скидки — наличие `discount`.
- `measureUnit` — `{ name, isDividable, step, divideValue, valueForPrice }`. Штучный: `name = "шт"`,
  `isDividable = false`. **Весовой:** `name = "кг"`, `isDividable = true`, `divideValue = 1000`;
  `price` — **цена за 1 кг**; `step` — шаг заказа в граммах (100…12000), к цене отношения не имеет.
  Признак весового товара берётся только отсюда.
- Наличие: `availabilityId = 3` («Доступен») или `0` («Недоступен», тогда может быть `price = 0`).
  В выдаче бывают позиции с отрицательным `itemId`, `price = 0` и без `extId` — заглушки, их
  отбрасывать. На 2026-11-21 в списках листьев были только доступные позиции; недоступные и
  заглушки встречались в других списках, поэтому фильтр всё равно нужен.
- Изображения: `mainImg`, `imgList[]` — абсолютные URL; ссылки на товар в API нет.
- Остальное (`zone`, `rack`, `wmsItemLocation*`, `nameplate`, `color`, `markCode`, `maxcount`) —
  внутренние поля склада, не сохраняются.

**Поиск** (`/catalog/client/search/platform/items`) честно отдаёт итог и уважает `pageSize`, но для
обхода категорий не нужен.

Цены переводятся в целые тенге, как требует `SourceProductSchema`.

Обход листа ограничен 100 страницами; номер страницы в ответе должен совпадать с запрошенным, иначе ошибка.

## Проверки

- **Юнит-тесты каркаса** (vitest, поддельный `fetch`, поддельные таймеры):
  - число одновременных запросов никогда не превышает лимит; темп не выше rps;
  - 429 с `Retry-After` в секундах и в виде даты; 5xx; таймаут; сетевая ошибка;
    4xx без повтора; исчерпание повторов даёт ошибку задачи, и новые задачи после неё не запускаются;
  - задачи, порождённые задачами; дедупликация; проверка итога категории; невалидный товар.
- **Тесты модуля Magnum** на обезличенных фикстурах ответов API: разбор цены, весовой признак,
  пагинация и конец листа по короткой странице, пустая страница, недоступные позиции и заглушки.
- **Тесты интеграции:** схема `SourceFile` с городом `Shymkent`; таблица категорий Magnum;
  отказ записи при `errorCount > 0`.
- **Локальный живой прогон** (после «да» на живой скрап): `pnpm scrape:magnum` пишет полный
  `magnum.json` без ошибок; по таблице категорий каждая из 12 публикуемых категорий содержит товары;
  `sourceStats` фиксирует время и счётчики. Сквозной прогон через `sync`, БД и `/api/szpt` —
  во втором проекте.
- Перед push: локальный CI (`pipeline`, `schema`, `security` и связанные группы).

## Решения, принятые в ходе обсуждения

- Пользователь: источник Magnum — API приложения Magnum Go, а не акции сайта и не Kaspi.

## Решения агента после проверки исполнителем

- **Наличие.** Go `ingest` пишет каждое предложение с `inStock = true`, поля наличия в `SourceProduct`
  нет. Поэтому модуль отдаёт только товары в наличии, если API даёт такой признак. Полнота
  проверяется до фильтра: число всех позиций, увиденных при пагинации категории, сравнивается
  с итогом API, если API его отдаёт (у Magnum не отдаёт, см. решение пользователя от 2026-11-21).
- **Сдвиг страниц во время обхода.** При расхождении с итогом категория скачивается заново один раз.
  Если расхождение повторилось, это ошибка категории. Для источников без итога не применяется.
- **Граница проекта.** Проект закончен, когда каркас и модуль Magnum слиты в `main` с зелёными
  тестами и локальный живой прогон дал полный `magnum.json`. Семь дней стабильности и сравнение
  скорости на Актау — это наблюдение после слияния, они решают вопрос о переносе.
- **Нераспознанная позиция Magnum** (не проходит схему, незнакомая единица или код наличия) — ошибка
  задачи, прогон останавливается и файл не пишется: fail-closed важнее полного списка плохих позиций
  за один прогон.
